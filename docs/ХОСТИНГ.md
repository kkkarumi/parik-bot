# Где и как размещать салоны

Цены здесь не указаны специально — ⚠️ проверяйте актуальные тарифы у провайдеров перед покупкой.

## Что где живёт

| Компонент | Где | Что хранит / через что проходит | Почему там |
|---|---|---|---|
| Бэкенд (API, напоминания) | VPS в РФ | — | рядом с базой; данные клиентов в РФ (локализация, 152-ФЗ ⚠️) |
| База данных PostgreSQL | VPS в РФ, тот же сервер | все данные салона: клиенты, записи, отзывы | то же |
| Бот (интерфейс) | VPS в РФ, тот же сервер | состояние незаконченных диалогов (`state.pickle`) | рядом с API |
| Бэкапы | VPS в РФ (`backups/`) + опционально внешнее хранилище | полная копия базы | внешнее — лучше тоже в РФ ⚠️ |
| Релей (Caddy) | VPS за границей (Турция / Казахстан / Европа) | ничего не хранит, только пересылает трафик к Telegram (видит его содержимое) | с серверов в РФ соединение с Telegram блокируется |
| Telegram | за рубежом | все сообщения бота | так устроен Telegram |
| Sentry (опционально) | за рубежом ⚠️ | сообщения об ошибках без телефонов и ключей | мониторинг сбоев |
| Uptime Kuma (опционально) | на VPS релея | только факт «жив/не жив» | должен быть вне сервера, который он проверяет |

```
Клиенты в Telegram ⇄ Telegram ⇄ релей (за рубежом) ⇄ VPS в РФ: бот + API + база (+ бэкапы)
```

## Две схемы размещения

### Схема 1. Папка на салон (как сейчас)

Каждый салон — своя копия проекта (`git clone … salon-имя`), свой `.env`, свои контейнеры `db + backend + bot`. Docker разводит их по имени папки.

**Плюсы**
- Полная изоляция: сбой, ошибка в настройке или удаление базы одного салона не задевает остальных.
- Просто объяснять и переносить: «база салона — вот этот том, бэкапы — вот эта папка». Расторжение договора = выгрузка и удаление одной папки.
- Код уже так работает, ничего переписывать не нужно.
- Можно обновлять салоны по одному (сначала свой «Парик», потом остальные).

**Минусы**
- Память: на каждый салон свой Postgres, API и бот. По README на 2 ГБ — 4–5 салонов.
- Обновление и мониторинг — N раз (скрипты помогают, но это N папок, N строк в cron).
- Нет общей статистики «по всем салонам».

### Схема 2. Общий бэкенд на всех

Один Postgres и один бэкенд на всех салонов (в модели данных уже есть `tenant_id` и ключ API на салон), плюс по процессу бота на салон.

**Плюсы**
- Экономия памяти и денег при 10+ салонах.
- Одно обновление, один мониторинг, одна база для бэкапа.

**Минусы**
- Сейчас **не готово**: установка, `manage.py`, бэкапы и восстановление рассчитаны на «один салон — одна база». Нужно переписать установку, выгрузку и удаление данных одного салона, восстановление одного салона из общего бэкапа.
- Ошибка в коде или миграции бьёт по всем салонам сразу.
- Для ПДн сложнее: данные разных операторов в одной базе — разграничение доступа должен обеспечивать код, юристу это тоже надо объяснить.
- Один упавший бэкенд = лежат все.

## Рекомендация

**Для первых 3–5 салонов — оставить схему 1** (папка на салон) на одном VPS в РФ + один релей за границей на всех.

Пересмотреть, когда:
- салонов больше, чем помещается на один VPS, и второй VPS дороже, чем время на переделку;
- или обслуживание N папок начинает отнимать заметное время.

Промежуточный шаг до схемы 2 — второй VPS в РФ и «размазать» салоны по двум серверам: та же схема 1, ничего переписывать не надо.

## Что выбирать при покупке

**VPS в РФ (бэкенд и базы)**
- Ubuntu 22.04/24.04, от 2 ГБ памяти на 4–5 салонов, диск от 20 ГБ (бэкапы!).
- Дата-центр в РФ (проверить в описании тарифа) ⚠️.
- Бэкапы/снимки диска у провайдера — приятный бонус, но не замена своим бэкапам.

**VPS релея**
- Самый дешёвый: 1 vCPU, 512 МБ (если ещё и Uptime Kuma — лучше 1 ГБ).
- **До покупки** проверить с российского VPS, что до этого провайдера/страны есть связь (`curl -m 10 https://сайт-провайдера`) ⚠️ — некоторые зарубежные подсети тоже бывают недоступны.
- Нужен домен или поддомен (см. [relay/README.md](../relay/README.md)).
